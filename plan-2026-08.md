# Plan: POST /articles/{slug}/report

Source spec: `spec-2026-08.md`. This plan follows the same file-by-file pattern already used for the closest existing feature in this codebase, `articles/{slug}/comments` (`CommentsApi.java` + `Comment`/`CommentRepository`/`CommentMapper`), with one deliberate structural difference: no check-then-insert. `ArticleFavoriteRepository.save()` does `if (mapper.find(...) == null) mapper.insert(...)` — fine for favorite/unfavorite, which is meant to be idempotent, but wrong here, since a report must reject the second attempt (AC2), not silently no-op it. The insert goes straight to the mapper and the composite primary key (`article_id`, `user_id`) is what actually enforces the rule.

## Files to touch

New files:
1. `src/main/resources/db/migration/V2__create_article_report_table.sql` — the migration from spec §4.
2. `src/main/java/io/spring/core/report/ArticleReport.java` — domain entity: `articleId`, `userId`, `reason`, `createdAt`. Uses `org.joda.time.DateTime` for `createdAt`, matching `Comment.java` and `Article.java` — not `java.time.Instant`. (This corrects an assumption in the peer-read notes on `spec-2026-08.md`, which guessed `Instant`; this repo's actual convention is Joda-Time throughout.) No surrogate `id` field, per spec.
3. `src/main/java/io/spring/core/report/ArticleReportRepository.java` — interface: `save(ArticleReport)`, `find(String articleId, String userId)`.
4. `src/main/java/io/spring/infrastructure/mybatis/mapper/ArticleReportMapper.java` — `@Mapper` interface: `insert(@Param("articleReport") ArticleReport)`, `find(@Param("articleId") String, @Param("userId") String)`.
5. `src/main/resources/mapper/ArticleReportMapper.xml` — MyBatis XML: plain `insert` (no existence check first) and a `find` select/resultMap, mirroring `ArticleFavoriteMapper.xml`'s shape.
6. `src/main/java/io/spring/infrastructure/repository/MyBatisArticleReportRepository.java` — `save()` calls `mapper.insert(...)` directly inside a `try/catch (DataIntegrityViolationException e)`, rethrowing as `DuplicateReportException` (see Risk 1 below for why this has to happen here and not at the controller-advice level).
7. `src/main/java/io/spring/api/exception/DuplicateReportException.java` — `extends RuntimeException`, message `"article already reported"` baked into the constructor, no `@ResponseStatus` — same shape as `InvalidAuthenticationException.java`.
8. `src/main/java/io/spring/api/ArticleReportApi.java` — controller, `@RequestMapping(path = "articles/{slug}/report")`, `@PostMapping`, `@PathVariable("slug") String slug`, `@AuthenticationPrincipal User user`, `@Valid @RequestBody ReportArticleParam`. Looks up the article via `articleRepository.findBySlug(slug).orElseThrow(ResourceNotFoundException::new)` (same as every other `articles/{slug}/...` endpoint). Also carries the package-private `ReportArticleParam` DTO at the bottom of the file (`@Getter @NoArgsConstructor @JsonRootName("report")`, `reason` field `@NotBlank(message = "can't be empty") @Size(max = 1000, message = "is too long")`), matching `CommentsApi.java`'s `NewCommentParam` pattern exactly.

Modified files:
9. `src/main/java/io/spring/api/exception/CustomizeExceptionHandler.java` — add `@ExceptionHandler(DuplicateReportException.class)` returning `422` with `{"message": "article already reported"}`, same flat shape as the existing `InvalidAuthenticationException` handler (and the `DataIntegrityViolationException` handler added in 2.2 — see Risk 1 for why this one has to be a distinct exception type, not the same handler).

New tests:
10. `src/test/java/io/spring/infrastructure/report/MyBatisArticleReportRepositoryTest.java` — `extends DbTestBase`, `@Import({MyBatisArticleReportRepository.class})`, mirrors `MyBatisArticleFavoriteRepositoryTest.java`.
11. `src/test/java/io/spring/api/ArticleReportApiTest.java` — `@WebMvcTest(ArticleReportApi.class)`, `extends TestWithCurrentUser`, mirrors `ArticleFavoriteApiTest.java`/`CommentsApi`'s test shape — covers AC1, AC2, AC4, AC5, AC6, AC7.

## Risks

**Risk 1 (real, found while planning, not while implementing): exception-type collision with 2.2's signup fix.** Homework 2.2 added a broad `@ExceptionHandler(DataIntegrityViolationException.class)` to `CustomizeExceptionHandler` for the signup race, returning `"username or email already exists"`. `@RestControllerAdvice` handlers are global — if `ArticleReportApi` also let a raw `DataIntegrityViolationException` escape from a duplicate-report insert, it would hit that *same* handler and return the wrong message for the wrong feature. Resolution: `MyBatisArticleReportRepository.save()` catches `DataIntegrityViolationException` at the source and rethrows it as the report-specific `DuplicateReportException`, so the raw exception never reaches the global dispatch for this path. This has to be decided now, at Plan time, not discovered while implementing task 2 — it's exactly the kind of thing that would otherwise ship as a confusing error message on the wrong feature.

**Risk 2: SQLite's exception translation is unverified.** This project's datasource is `org.sqlite.JDBC` (`application.properties`). Spring's default `SQLErrorCodesTranslator` doesn't ship SQLite-specific error codes, so whether a UNIQUE-constraint violation from the xerial SQLite driver reliably translates to `DataIntegrityViolationException` (versus falling through to a generic `UncategorizedSQLException`, which `MyBatisArticleReportRepository`'s catch block wouldn't match) is not something to assume — it's exactly what the repository test in task 1 has to prove empirically, against the real test database, not a mock.

**Risk 3: `Page.java`-style silent clamping doesn't apply here, but a related boundary question does.** `reason` needs both `@NotBlank` and `@Size(max = 1000)` (AC6/AC7) — Bean Validation handles both cleanly, so this isn't actually a risk once named, but it's worth stating explicitly since spec-2026-08.md's own first draft got this wrong (documented `varchar(1000)` with "no length cap," caught in peer review) — a plan that didn't call this out explicitly would risk repeating the same gap at implementation time.

## Evaluate (written after implementing task 1)

**Does any step say "figure out later"?** No — Risk 1 (the exception-collision with 2.2) was resolved at plan time with a specific design decision (catch-and-rethrow inside the repository), not deferred.

**Does the spec still match the code?** Mostly, with one place the spec is now stale rather than the code having drifted: `spec-2026-08.md`'s Constraints section left "catch the DB constraint violation directly, or check-then-insert" as an open question. Task 1 answers it (catch directly), but the spec doesn't yet mention that this required *two* catch blocks because of SQLite's exception translation gap — that's new information task 1 produced, not something the spec got wrong. Worth a follow-up edit to the spec before 2.5, not urgent enough to block this task.

**One strength of the plan:** naming Risk 1 (the 2.2/2.3 exception-type collision) before writing any code. That bug would have been genuinely confusing to debug later — a report endpoint returning "username or email already exists" — and there would have been nothing pointing back to 2.2 as the cause.

**One weakness:** Risk 2 said the SQLite exception-translation behavior was "unverified" and should be "proven empirically by the repository test," which was the right instinct, but the plan stopped at naming the uncertainty rather than sketching what the fallback would look like if the assumption failed. It turned out to fail (see below), and the fix had to be designed reactively during Verify rather than being a plan-time decision.

**One adjustment made before finishing task 1:** the repository test failed on the very case Risk 2 was worried about — `DataIntegrityViolationException` never fired; the real exception was `UncategorizedSQLException` wrapping `org.sqlite.SQLiteException`. Added a second `catch` block in `MyBatisArticleReportRepository.save()` that checks the SQLite result code (`SQLITE_CONSTRAINT*`) before treating it as a duplicate, so a non-constraint SQL error doesn't get silently mislabeled. Re-ran the test: passed, 75/75 full suite green.
