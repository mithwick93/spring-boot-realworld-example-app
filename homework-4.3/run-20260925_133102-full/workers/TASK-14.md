# Worker Report: TASK-14

## Task
SCOPE: src/main/java/io/spring/application/article/DuplicatedArticleUpdateValidator.java
QUESTION: Does this cross-parameter validator correctly wire the article-id exclusion into the duplicate-title check on update?

## Findings
- `DuplicatedArticleUpdateValidator.java:20-21` — `value[0]` is cast to the current `Article` (the article being updated) and `value[1]` to `UpdateArticleParam` (the incoming, untrusted request body). This matches the cross-parameter validator signature used for the update endpoint.
- `DuplicatedArticleUpdateValidator.java:22-25` — if the incoming `title` is empty/blank, the validator short-circuits to valid (no duplicate check performed). This is intentional (no title change requested) but relies on `UpdateArticleParam` having no `@NotBlank`/`@Size` constraint of its own — `UpdateArticleParam.java:13-16` declares `title`/`body`/`description` as plain `String` fields with no Bean Validation annotations at all. Per CLAUDE.md's Input Validation section ("Validate format and required fields via Bean Validation... add `@Size` bounds on any new user-supplied string field"), this DTO currently has no upper bound on title length — not a defect in the exclusion logic itself, but an adjacent gap worth flagging since this validator is the only guard touching `title`.
- `DuplicatedArticleUpdateValidator.java:26-29` — if the newly-derived slug equals the current article's own slug, it also short-circuits to valid. This is a redundant-but-harmless optimization: even without this check, the exclusion filter below would already exclude the current article and yield the same "not duplicated" result.
- `DuplicatedArticleUpdateValidator.java:30-34` — **this is the actual id-exclusion wiring**: `articleRepository.findBySlug(newSlug).filter(existing -> !existing.getId().equals(article.getId())).isPresent()`. This correctly excludes the article being updated from counting as a duplicate of itself — i.e., renaming an article to a slug it already owns, or leaving the title effectively unchanged in slug form, will not be flagged as a false positive.
- `DuplicatedArticleUpdateValidator.java:38-44` — on violation, `disableDefaultConstraintViolation()` + `addParameterNode(1).addPropertyNode("title")` produces the 3-segment property path (`updateArticle.<param>.title`) that CLAUDE.md's Conventions section documents as required for both `CustomizeExceptionHandler.getParam` and `GraphQLCustomizeExceptionHandler.getParam` to correctly resolve the field name. `addParameterNode(1)` correctly targets `value[1]` (the `UpdateArticleParam`), matching the parameter actually inspected.
- `DuplicatedArticleConstraint.java:24` — `validationAppliesTo() default ConstraintTarget.IMPLICIT` is present, which CLAUDE.md flags as a required annotation attribute once a `@Constraint` has both a generic (`DuplicatedArticleValidator`) and cross-parameter (`DuplicatedArticleUpdateValidator`) validator registered (`DuplicatedArticleConstraint.java:14`). This is correctly set, avoiding the `ConstraintDefinitionException: mixes generic and cross-parameter validation` pitfall.
- Not evaluated here (out of scope per the question, but adjacent): the check-then-act gap between `findBySlug` (line 32) and the eventual persistence of the update is a classic TOCTOU window. CLAUDE.md's Test Plan section explicitly calls out `Duplicated*Validator` as having "a documented history of TOCTOU races" — this validator's id-exclusion logic is correct, but the race itself (two concurrent updates to different articles both renaming to the same new slug) is a pre-existing, separately-tracked class of risk, not something this validator's exclusion wiring introduces or fixes.

## Recommendations
No gap was found in the article-id exclusion logic itself — `DuplicatedArticleUpdateValidator.java:33` correctly excludes the article being updated from its own duplicate-title check, and the violation is wired to the correct parameter/field path per this repo's documented convention.

Two adjacent, lower-priority items worth a follow-up (not blocking, not part of the exclusion-wiring question):
1. Add `@Size` (and consider `@NotBlank`) bounds to `UpdateArticleParam.title`/`body`/`description` (`UpdateArticleParam.java:13-16`) per CLAUDE.md's Input Validation requirement that any user-supplied string field carry a `@Size` bound — currently an attacker could submit an arbitrarily large `title` and it would only be rejected if it happens to collide with an existing slug.
2. If not already covered elsewhere, confirm test coverage exists for the specific race CLAUDE.md flags (concurrent updates to two different articles both renaming to the same slug) — this validator's correctness under a single request is confirmed, but TOCTOU coverage is a separate concern from what was asked here.
