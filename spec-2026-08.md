# Spec: POST /articles/{slug}/report

## 1. Functional Requirements

This is a new endpoint that lets an authenticated user report an article for a reason (spam, abuse, off-topic, etc.). It's a new capability, not a fix to an existing one — the repo has no reporting/moderation concept today.

- FR1: A logged-in user can submit a report against any existing article by slug, providing a free-text reason.
- FR2: A user can report a given article at most once. A second report attempt by the same user against the same article is rejected — not silently accepted, not silently ignored.
- FR3: The one-report-per-user-per-article rule holds even under concurrent duplicate requests, not only sequential ones — enforced at the database level (see Constraints), not by an application-layer check alone.
- FR4: Reporting an article does not require the reporter to be someone other than the article's author — self-reporting is allowed, matching the repo's existing favorite/unfavorite endpoints, which impose no such restriction either.
- FR5: A report is a create-only record. There is no endpoint to view, list, retract, or resolve a report in this spec (see Out of Scope).
- FR6: Reporting a nonexistent article (bad slug) returns a not-found error, matching the existing `ArticleFavoriteApi` behavior for the same case.
- FR7: Reporting without authentication is rejected before any article lookup happens, matching the existing security filter behavior for the rest of the API.

## 2. Acceptance Criteria (GIVEN/WHEN/THEN)

**AC1 — Successful report**
GIVEN an authenticated user "jake" and an existing article with slug "how-to-train-your-dragon" that "jake" has not previously reported
WHEN "jake" sends `POST /articles/how-to-train-your-dragon/report` with a non-blank `reason`
THEN the response is `201 Created` with a `report` envelope containing the article's slug, the reason submitted, and a creation timestamp
AND a row exists in `article_report` for `(article_id, jake's user_id)`.

**AC2 — Duplicate report by the same user**
GIVEN "jake" has already reported article "how-to-train-your-dragon"
WHEN "jake" sends `POST /articles/how-to-train-your-dragon/report` again (same or different reason text)
THEN the response is `422 Unprocessable Entity` with body `{"message": "article already reported"}`
AND no second row is written — the existing report is untouched.

**AC3 — Different users can each report the same article once**
GIVEN "jake" has already reported article "how-to-train-your-dragon"
WHEN a different authenticated user "jane" sends `POST /articles/how-to-train-your-dragon/report` for the first time
THEN the response is `201 Created`, identical in shape to AC1
AND both "jake"'s and "jane"'s reports exist as separate rows.

**AC4 — Article does not exist**
GIVEN no article exists with slug "no-such-article"
WHEN an authenticated user sends `POST /articles/no-such-article/report` with a non-blank `reason`
THEN the response is `404 Not Found` with no JSON body (matching `ResourceNotFoundException`'s existing bare-404 behavior — see Constraints).

**AC5 — Unauthenticated request**
GIVEN no valid authentication token is presented (missing or invalid JWT)
WHEN a request is sent to `POST /articles/{slug}/report` for any slug, existing or not
THEN the response is `401 Unauthorized` with no JSON body, and no article lookup or DB write occurs.

**AC6 — Missing or blank reason**
GIVEN an authenticated user and an existing, not-yet-reported article
WHEN the request body omits `reason` or submits it as blank/whitespace-only
THEN the response is `422 Unprocessable Entity` with body `{"errors": {"reason": ["can't be blank"]}}`, matching the existing field-validation error shape used elsewhere in the API (e.g. `NewArticleParam`).

**AC7 — Reason exceeds column width**
GIVEN an authenticated user and an existing, not-yet-reported article
WHEN `reason` is longer than 1000 characters
THEN the response is `422 Unprocessable Entity` with body `{"errors": {"reason": ["size must be between 0 and 1000"]}}` — the same Bean Validation path as AC6, not a DB-level error.

## 3. Input / Output Examples

**Request — successful report (AC1)**
```
POST /articles/how-to-train-your-dragon/report
Authorization: Token <jwt>
Content-Type: application/json

{
  "report": {
    "reason": "This article contains plagiarized content from another site."
  }
}
```

**Response — 201 Created (AC1)**
```json
{
  "report": {
    "articleSlug": "how-to-train-your-dragon",
    "reason": "This article contains plagiarized content from another site.",
    "createdAt": "2026-08-31T10:15:00.000Z"
  }
}
```

**Response — 422, duplicate report (AC2)**
```json
{
  "message": "article already reported"
}
```

**Response — 404, bad slug (AC4)**
```
(empty body, HTTP 404)
```

**Response — 401, unauthenticated (AC5)**
```
(empty body, HTTP 401)
```

**Response — 422, blank reason (AC6)**
```json
{
  "errors": {
    "reason": ["can't be blank"]
  }
}
```

## 4. Constraints

Real limits this implementation must respect:

- Must not modify the existing `articles` or `users` tables — additive-only migration (`V2__create_article_report_table.sql`; current schema is a single `V1__create_tables.sql`).
- Must reuse the existing JWT bearer-token auth already enforced by `WebSecurityConfig` — no new auth mechanism, no new permission key.
- Must not call any external service (moderation queue, notification, email) — a report is a single local DB write, synchronous or otherwise out of scope (see Out of Scope).
- Must not add a new runtime dependency — uniqueness enforcement uses existing Spring Data/MyBatis/Flyway tooling only.

Design decisions:

- **Request envelope**: request body is wrapped under a root key matching the resource name (`{"report": {...}}`), the same shape `NewArticleParam`/`UpdateUserParam` use via `@JsonRootName`. `reason` is `@NotBlank` and `@Size(max = 1000)`, matching the `article_report.reason` column width (an earlier draft left this uncapped, which would have let an over-length reason hit an unhandled DB error instead of a clean validation response — caught during peer read, see peer-read-notes-2026-08.md); no category/enum in this iteration.
- **DB schema** — composite primary key, following the `article_favorites` pattern already in `V1`:
  ```sql
  create table article_report (
    article_id varchar(255) not null,
    user_id varchar(255) not null,
    reason varchar(1000) not null,
    created_at timestamp not null,
    primary key (article_id, user_id)
  );
  ```
  This is what makes AC2 a DB-level guarantee rather than an application-layer race — the second insert fails at the database, not after an earlier `SELECT`-then-`INSERT` window.
- **Error shape for AC2**: this repo already has three error shapes depending on exception type — bare 404 (`ResourceNotFoundException`, no handler entry), flat `{"message": ...}` (`InvalidAuthenticationException`), and `{"errors": {field: [...]}}` (Bean Validation). A duplicate report is a business-rule violation, not a field or auth failure, so this follows the closest existing precedent — flat `{"message": ...}`, via a new `DuplicateReportException` mapped in `CustomizeExceptionHandler` — rather than inventing a fourth shape.
  **Resolved in 2.3 (was an open question at spec time):** `MyBatisArticleReportRepository.save()` inserts directly and catches the DB-level violation, rather than check-then-insert. This needed two catch blocks, not one — this project's SQLite datasource doesn't get Spring's standard `DataIntegrityViolationException` translation for constraint violations; the real exception is `org.springframework.jdbc.UncategorizedSQLException` wrapping `org.sqlite.SQLiteException`, confirmed by the repository test failing against the real driver before this was known, not assumed upfront. Both are caught and rethrown as `DuplicateReportException`.
  **Assumption surfaced at the 2.4 review gate, accepted explicitly rather than fixed:** this translation lives inside the repository implementation, and homework 2.2's signup fix independently added its own bespoke `DataIntegrityViolationException` handling in the same style. Two instances of the same pattern, each hand-rolled per feature, is not a scalable design if this repo accumulates more uniqueness constraints — a shared "insert and translate duplicate-key" helper would be the more senior-engineer-approved answer. Not doing that refactor now: it would touch already-committed, already-tested code from 2.2 and 2.3 for a generalization neither current feature strictly needs, which is more scope than "wire the report endpoint to HTTP" calls for. Named here as a real, deliberate deferral, not an oversight.
- **Test naming**: `should_<outcome>_<condition>` per repo convention, e.g. `should_report_an_article_success`, `should_return_422_when_article_already_reported`. Controller tests: `@WebMvcTest(ArticleReportApi.class)`. Repository tests: extend `DbTestBase` (`@MybatisTest`), per `ArticleFavoriteApiTest` / `MyBatisArticleFavoriteRepositoryTest`.

## 5. Out of Scope

- Viewing, listing, or counting reports (no `GET` endpoint of any kind for reports).
- Retracting or editing a submitted report.
- Any admin/moderator review workflow, dashboard, or resolution status for reports.
- Automatic takedown, hiding, or flagging of an article based on report volume.
- Notifications to the article's author, to moderators, or to the reporting user.
- Rate limiting on report submissions.
- A fixed reason category/enum (e.g. `SPAM`, `ABUSE`, `OFF_TOPIC`) — this spec uses free-text `reason` only.
- GraphQL support — this spec covers the REST adapter (`ArticleReportApi`) only; whether this extends to the GraphQL adapter is a separate decision.
