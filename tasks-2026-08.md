**Done when:** `ArticleReportApiTest` passes for AC1 (201), AC2 (422 duplicate), AC3 (201, different user, separate row), AC4 (404 bad slug), AC5 (401 unauthenticated), AC6 (422 blank reason), AC7 (422 over-length reason); full suite green; commit lands.

**Caught at the 2.4 review gate (2026-09-02):** this line originally listed six ACs, not seven, despite the task description above claiming "all seven acceptance criteria" — AC3 (different users can each report the same article once) was missing. Nothing about the *implementation* needs to change for AC3 to pass — `save()` inserts one row per `(articleId, userId)` pair, so two different users each reporting the same article is already the expected behavior, not a new code path — but the test list needs to actually say so, since an untested acceptance criterion is exactly the kind of thing that's easy to silently drop between planning and implementation. See `review-gate-2026-08.md` for the full gate writeup.

**Status (2026-09-02, homework 2.5):** implemented, verified, and committed (`d772787`) — all 7 tests in `ArticleReportApiTest` pass (AC1–AC7), full suite 82/82 green (75 baseline + 7 new). One real gap caught while implementing, not assumed from the sibling pattern: `plan-2026-08.md`'s DTO sketch specified `@NotBlank(message = "can't be empty")`, copying `CommentsApi`'s `NewCommentParam` message text verbatim — but `spec-2026-08.md`'s AC6 requires the exact string `"can't be blank"`, a different message. Using the plan's message as written would have passed a "does it validate" smoke test but failed AC6's wire-contract assertion. Fixed by using `@NotBlank(message = "can't be blank")` in `ReportArticleParam`; `@Size(max = 1000)` needed no custom message since Bean Validation's default text ("size must be between 0 and 1000") already matches AC7 verbatim.
